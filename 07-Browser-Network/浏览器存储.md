# 浏览器存储：Cookie、Storage、IndexedDB 怎么选？

> 浏览器存储就像电脑里的不同收纳空间：有的适合随请求带给服务器，有的适合保存少量设置，有的适合存大量结构化数据。选错位置，可能影响性能和安全。

## 一、常见浏览器存储方式 ⭐⭐⭐

| 类型 | 主要用途 | 是否自动随 HTTP 请求发送 | 特点 |
|---|---|---|---|
| Cookie | 会话标识、少量状态 | 符合规则时会 | 有过期时间、域、路径、安全属性 |
| localStorage | 本地设置、非敏感偏好 | 否 | 同源共享、长期保存、同步 API |
| sessionStorage | 当前标签页会话数据 | 否 | 通常随标签页会话存在 |
| IndexedDB | 大量结构化数据、离线数据 | 否 | 异步、支持索引和事务 |
| Cache Storage | 缓存请求和响应 | 否 | 常与 Service Worker 配合 |

## 二、Cookie ⭐⭐⭐

Cookie 是浏览器保存的一小段数据。服务器可以通过 Set-Cookie 设置，浏览器在后续符合规则的请求中自动携带。

服务器设置：

~~~http
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Path=/
~~~

常见属性：

- **Expires / Max-Age**：设置过期时间。没有明确过期时间的 Cookie 通常是会话 Cookie，但浏览器可能有会话恢复等行为。
- **Domain**：控制哪些域名可以使用 Cookie。
- **Path**：控制适用路径。
- **Secure**：只通过安全连接发送。
- **HttpOnly**：禁止 JavaScript 通过 document.cookie 读取。
- **SameSite**：限制跨站请求时是否携带。

### Cookie 的特点

- 请求匹配时会自动发送给服务器。
- 体积较小，不适合保存大量数据。
- 可能增加每次请求的头部开销。
- 适合会话标识等场景，但需要正确设置安全属性。

不要把密码或完整用户资料直接放进 Cookie。通常保存的是服务端可识别的会话凭据。

## 三、localStorage ⭐⭐⭐

localStorage 是 Web Storage API 的一部分，按源隔离。

~~~javascript
// 保存
localStorage.setItem("theme", "dark");

// 读取
const theme = localStorage.getItem("theme");

// 删除一项
localStorage.removeItem("theme");

// 清空当前源的 localStorage
localStorage.clear();
~~~

特点：

- 同源页面通常共享。
- 关闭浏览器后通常仍然保留，除非用户或浏览器清理。
- API 是同步的，读取和写入大数据可能阻塞主线程。
- 数据不会自动附加到 HTTP 请求。
- 不提供 HttpOnly 保护，同源脚本可以读取。

适合保存主题、语言、非敏感偏好等数据。不建议把高敏感会话凭据随意放在 localStorage，因为 XSS 可以读取它。

## 四、sessionStorage ⭐⭐

用法和 localStorage 类似：

~~~javascript
sessionStorage.setItem("draft", "正在编辑的内容");
const draft = sessionStorage.getItem("draft");
~~~

特点：

- 按源和顶级浏览上下文（通常可理解为标签页会话）隔离。
- 页面刷新后通常仍然存在。
- 标签页会话结束后通常清除。
- 新开标签页通常有独立的 sessionStorage；通过带 opener 的窗口打开时，初始状态可能被复制，之后各自独立。

适合临时表单状态、单个标签页的操作流程等。

## 五、IndexedDB ⭐⭐⭐

IndexedDB 是浏览器提供的异步客户端数据库，适合保存大量结构化数据。

适合场景：

- 离线应用数据。
- 大量记录和索引查询。
- 复杂表单草稿。
- 需要在本地持久化的业务数据。

基本思路：

1. 打开或创建数据库。
2. 创建 object store（对象仓库）。
3. 在事务中读取、写入数据。
4. 需要时通过索引查询。
5. 处理成功、失败和事务完成事件。

原生 API 示例（展示核心结构，实际项目建议封装错误处理）：

~~~javascript
const request = indexedDB.open("app-db", 1);

request.onupgradeneeded = (event) => {
  const db = event.target.result;
  if (!db.objectStoreNames.contains("users")) {
    db.createObjectStore("users", { keyPath: "id" });
  }
};

request.onsuccess = (event) => {
  const db = event.target.result;
  const tx = db.transaction("users", "readwrite");
  tx.objectStore("users").put({ id: 1, name: "Tom" });
};
~~~

IndexedDB 是异步 API，并支持事务和索引，比 localStorage 更适合大量结构化数据。

## 六、Cache Storage

Cache Storage 是浏览器 Cache API 提供的存储空间，通常与 Service Worker 一起用于离线和资源缓存。

~~~javascript
const cache = await caches.open("static-v1");
await cache.add("/styles.css");

const response = await cache.match("/styles.css");
~~~

Cache Storage 保存的是 Request / Response 对象，不等同于 localStorage，也不等同于浏览器自动管理的 HTTP 缓存。

## 七、存储容量和生命周期

不要死记“每种存储固定只能存多少 MB”。容量会受到浏览器、设备空间、隐私模式、用户策略和站点配额影响。

- Cookie 通常有较严格的单项大小和数量限制。
- Web Storage 适合少量字符串数据。
- IndexedDB 和 Cache Storage 更适合大量数据，但也有配额与清理策略。
- 用户可以清除网站数据；浏览器也可能在存储压力下回收非持久化数据。

如果应用确实需要持久化能力，可以了解 StorageManager API，例如估算使用量和申请持久化存储，但浏览器是否批准由实现和策略决定。

## 八、不同存储方式怎么选？

| 需求 | 推荐考虑 |
|---|---|
| 服务端识别登录会话 | Cookie（配合 HttpOnly、Secure、SameSite 等） |
| 主题、语言、非敏感偏好 | localStorage |
| 当前标签页临时流程 | sessionStorage |
| 大量结构化离线数据 | IndexedDB |
| 离线缓存请求和响应 | Cache Storage / Service Worker |

## 九、常见安全问题

- localStorage 和 sessionStorage 中的数据可被同源 JavaScript 读取，XSS 可能窃取。
- Cookie 如果没有 HttpOnly，可能被脚本读取。
- Cookie 如果没有合理的 SameSite 和 CSRF 防护，可能被跨站请求滥用。
- 不要把 API 私钥、数据库密码等服务端秘密放在浏览器端。
- 用户可以修改浏览器存储，不能把本地数据当成可信权限依据。
