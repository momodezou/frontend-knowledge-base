# HTTPS 与 TLS：为什么 HTTPS 比 HTTP 安全？

> HTTP 像把明信片交给邮递员：路上可能被别人看到或篡改。HTTPS 则像把明信片装进带锁的信封，并确认收件人身份。

## 一、HTTPS 是什么？⭐⭐⭐

HTTPS = HTTP + TLS。

- HTTP 负责定义请求和响应的语义。
- TLS 负责在通信双方之间建立加密保护。
- HTTPS 通常使用 443 端口。

HTTPS 主要提供三项安全能力：

1. **机密性**：通信内容被加密，旁观者不容易读懂。
2. **完整性**：通信内容如果被篡改，可以被检测出来。
3. **身份认证**：浏览器可以通过证书验证自己连接的服务器身份。

注意：HTTPS 不代表网站本身一定可信，也不代表网站没有漏洞。它主要保护浏览器与服务器之间的通信链路。

## 二、为什么需要加密？

假设用户登录网站，发送账号密码。

如果使用未加密的 HTTP，网络路径上的攻击者在某些条件下可能监听或篡改数据。

HTTPS 使用 TLS 为 HTTP 通信建立保护，降低窃听、篡改和冒充服务器的风险。

## 三、对称加密与非对称加密 ⭐⭐⭐

### 1. 对称加密

加密和解密使用同一把密钥。

生活例子：你和朋友各持有同一把钥匙，用它锁箱子和开箱子。

优点：速度快，适合加密大量数据。

问题：通信双方怎样安全地拿到同一把密钥？

### 2. 非对称加密

使用一对密钥：

- 公钥：可以公开给别人。
- 私钥：必须由持有者妥善保管。

用公钥加密的数据，通常由对应私钥解密；数字签名则是用私钥签名，由公钥验证。

优点：适合身份验证、密钥协商或签名等用途。

问题：计算开销通常比对称加密大，不适合直接加密大量网页数据。

### 3. HTTPS 为什么两种都用？

TLS 握手阶段使用证书和密钥协商机制建立安全会话，随后通常使用协商出的对称密钥加密大量应用数据。

**好记版：非对称密码学帮助建立信任和密钥；对称加密负责高效传输数据。**

## 四、数字证书是什么？⭐⭐⭐

数字证书可以理解为服务器的“网络身份证”。

证书通常包含：

- 网站域名等身份信息。
- 证书持有者的公钥。
- 证书有效期。
- 颁发者信息。
- CA 的数字签名等。

CA（Certificate Authority，证书颁发机构）负责按照证书体系签发证书。

浏览器验证证书时，会检查证书链、签名、有效期、域名匹配等信息，并依据受信任的根证书建立信任链。

**注意：** 证书里有公钥，不代表证书天然可信。关键是证书链是否能验证到浏览器信任的根。

## 五、TLS 握手大致做了什么？⭐⭐⭐

不同 TLS 版本握手细节不同。以 TLS 1.3 的典型完整握手为例，简化理解：

1. **ClientHello**：客户端告诉服务器支持的 TLS 版本、密码套件、随机数和密钥协商参数等。
2. **ServerHello**：服务器选择参数，并发送自己的密钥协商信息。
3. **服务器发送证书和认证信息**：客户端验证证书链、域名、有效期等。
4. **双方计算会话密钥**：通过密钥协商得到相同的共享秘密，再派生出会话密钥。
5. **握手完成**：双方确认握手消息，之后使用对称密钥保护应用数据。

TLS 1.3 支持更精简的握手流程；恢复会话时还可能使用 PSK，某些场景可使用 0-RTT，但 0-RTT 存在重放风险，不是所有请求都适合。

## 六、数字签名与证书验证

数字签名不是“把内容加密一下”。

它主要用于证明：

- 签名由对应私钥持有者产生。
- 被签名的数据没有被悄悄修改。

证书签名帮助浏览器确认：某个受信任的 CA 为证书中的身份与公钥背书。

## 七、HTTP 和 HTTPS 的区别

| 对比 | HTTP | HTTPS |
|---|---|---|
| 是否加密 | 默认不加密 | 通过 TLS 加密 |
| 数据完整性保护 | 不提供 TLS 级保护 | 提供 |
| 服务器身份认证 | 不提供 TLS 证书认证 | 可验证证书身份 |
| 常见默认端口 | 80 | 443 |
| 性能 | 无 TLS 握手开销 | 有握手成本，但现代 TLS、连接复用和硬件加速已大幅降低影响 |

## 八、前端开发中怎样排查 HTTPS 问题？

常见问题：

- 证书过期。
- 证书域名不匹配。
- 证书链不完整。
- 页面通过 HTTPS 加载，却请求不安全的 HTTP 资源，触发 Mixed Content（混合内容）限制。
- 本地开发环境证书未被系统或浏览器信任。

排查时查看浏览器地址栏安全信息、DevTools Console/Network，以及服务器证书配置。
