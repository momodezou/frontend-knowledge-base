# 前端常见设计模式：把重复问题变成可复用的方案

> **通俗理解**：设计模式不是必须背的“高级套路”，而是很多开发者在相似问题中总结出来的常见解决思路。关键不是模式名字，而是**什么问题适合用、用了有什么代价**。

## 一、先判断是否真的需要设计模式 ⭐⭐⭐

例如，一个按钮只有一个点击回调，就不需要专门写一个事件总线；一个工具函数只有一次调用，也不一定需要复杂的工厂。

**核心原则**：代码先清晰，再考虑复用。为了“套模式”把简单问题复杂化，反而会降低可维护性。

## 二、工厂模式（Factory）：统一创建不同对象 ⭐⭐⭐

**场景**：同一种业务实体有多个类型，例如通知消息可能是成功、警告、错误。

```javascript
function createNotification(type, message) {
  const styles = {
    success: { icon: '✓', color: 'green' },
    warning: { icon: '!', color: 'orange' },
    error: { icon: '×', color: 'red' }
  };
  const style = styles[type] ?? styles.warning;
  return { type, message, ...style };
}

console.log(createNotification('success', '保存成功'));
```

**为什么使用工厂？** 让对象的创建规则集中管理，调用方不必关心内部细节。

**常见误区**：不是所有 `new` 都需要封装成工厂；对象创建很简单时直接创建更清晰。

## 三、单例模式（Singleton）：共享一个实例 ⭐⭐

**场景**：应用中希望共享同一个服务对象，例如日志配置或受控的连接管理器。

```javascript
class Logger {
  log(message) { console.log(`[app] ${message}`); }
}

const logger = new Logger();
export { logger }; // 同一模块实例的导出通常被模块系统缓存和复用
```

**注意**：单例并不等于“任何地方都应该拿全局变量”。过多单例可能形成隐式依赖，测试时难以隔离状态；不同运行环境、不同模块实例/进程之间也不保证共享同一个内存实例。

## 四、发布订阅模式（Pub/Sub）：让模块解耦 ⭐⭐⭐

**通俗理解**：像订阅公众号。发布方只发消息，不必知道具体谁会阅读；订阅方选择自己关心的主题。

```javascript
function createEventBus() {
  const events = new Map();

  return {
    on(type, handler) {
      if (!events.has(type)) events.set(type, new Set());
      events.get(type).add(handler);
      return () => events.get(type)?.delete(handler); // 返回取消订阅函数
    },
    emit(type, payload) {
      for (const handler of events.get(type) ?? []) handler(payload);
    }
  };
}

const bus = createEventBus();
const off = bus.on('saved', (id) => console.log('保存完成', id));
bus.emit('saved', 42);
off();
```

**实际用途**：低耦合的事件通知、跨模块事件，但大规模状态同步更适合明确的数据流或状态管理方案。

**易错点**：监听器不解绑可能让闭包长期持有不再需要的对象；事件名也要规范，否则难以追踪调用链。

### 观察者模式和发布订阅有什么区别？

- 观察者模式：被观察对象通常直接维护观察者列表并通知。
- 发布订阅：通常通过事件通道或中介协调发布者和订阅者。

现实框架中两个词可能被宽松地使用，面试更重要的是说明通信和耦合关系。

## 五、策略模式（Strategy）：把多种算法/规则放进映射 ⭐⭐⭐

**场景**：订单按会员等级采用不同折扣规则。

```javascript
const pricingStrategies = {
  normal: (price) => price,
  vip: (price) => price * 0.9,
  svip: (price) => price * 0.8
};

function getPrice(level, price) {
  const strategy = pricingStrategies[level] ?? pricingStrategies.normal;
  return strategy(price);
}
```

与大量 if/else 相比，策略映射方便扩展新的规则，也利于单独测试。

**提醒**：客户端计算只用于显示预估，真正的优惠计算和结算价格必须由服务端验证。

## 六、适配器模式（Adapter）：把不一致的接口转换成统一接口 ⭐⭐⭐

**场景**：两个后端接口返回的数据字段不同，前端组件却希望使用统一格式。

```javascript
function adaptOldUser(raw) {
  return { id: raw.user_id, name: raw.user_name };
}
function adaptNewUser(raw) {
  return { id: raw.id, name: raw.displayName };
}

// UI 只依赖统一的 { id, name } 结构
```

优势：把差异集中到边界层，避免每个组件都写大量字段兼容逻辑。

**易错点**：适配器不是无条件吞掉所有缺失字段。对于关键字段缺失，还需要明确校验和错误处理。

## 七、装饰器思想（Decorator）：不改原功能，叠加新能力 ⭐⭐

例如给请求函数加耗时统计：

```javascript
function withTiming(fn) {
  return async (...args) => {
    const start = performance.now();
    try {
      return await fn(...args);
    } finally {
      console.log('耗时(ms)：', performance.now() - start);
    }
  };
}

const timedFetch = withTiming(fetch);
```

把日志、重试、权限检查等横切能力通过包装函数组合起来，是装饰器思想的一种体现。

**区别**：这里指通用设计模式，不等于 TypeScript/JavaScript 的 `@decorator` 语言语法完全相同。

## 八、设计模式怎么选？

| 你遇到的问题 | 可以考虑 | 可能的代价 |
| --- | --- | --- |
| 创建对象规则复杂且重复 | 工厂 | 多一层封装 |
| 确实需要全局共享一份服务 | 单例 | 隐式状态、测试困难 |
| 多个模块需要接收事件 | 发布订阅 | 难追踪、忘记解绑 |
| 有多套可替换业务算法 | 策略 | 需要管理策略表 |
| 第三方数据格式不一致 | 适配器 | 边界逻辑增加 |
| 给已有函数叠加横切能力 | 装饰器 | 包装层次过多时调试困难 |

## 九、真实项目思考题

假设你在管理系统中开发：

1. 两个业务 API 的字段不同 —— 可以在哪里使用适配器？
2. 权限不同，对按钮执行不同规则 —— 策略与直接 if/else 怎么取舍？
3. 某个全局事件总线导致页面卸载后仍执行回调 —— 怎么排查？
4. 所有请求都需要统一记录耗时 —— 适合怎样的包装方式？
