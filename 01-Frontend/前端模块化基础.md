# 前端模块化基础：把大代码拆成容易维护的小模块

> **通俗理解**：模块化就像把厨房的洗菜、切菜、炒菜分工明确。每个模块只负责相对独立的事情，通过明确的接口协作，避免所有代码写在一起。

## 一、为什么需要模块化？ ⭐⭐⭐

如果一个项目把所有函数都写在一个 JS 文件里，容易出现：

- 命名冲突：多个文件都定义 `init()`。
- 依赖混乱：不知道某段代码依赖哪个变量。
- 修改风险大：改一个功能影响其他功能。
- 测试困难：很难单独测试一段代码。

模块化主要解决**作用域隔离、代码复用、依赖管理和职责清晰**。

## 二、ES Modules：现代浏览器和前端项目的主流模块 ⭐⭐⭐

### 导出：export

```javascript
// math.js
export const PI = 3.14159;
export function add(a, b) {
  return a + b;
}
```

### 导入：import

```javascript
// main.js
import { add, PI } from './math.js';
console.log(add(1, 2), PI);
```

HTML 中直接运行原生 ESM：

```html
<script type="module" src="./main.js"></script>
```

**注意：** 直接在浏览器中使用 ESM，应该通过本地 HTTP 开发服务器访问，而不是直接使用 `file://`，否则可能遇到模块加载/CORS 限制。

## 三、命名导出和默认导出的区别 ⭐⭐⭐

```javascript
// user.js
export const role = 'editor';
export default function getUser() {
  return { name: 'Tom' };
}
```

```javascript
import getUser, { role } from './user.js';
```

| 对比 | 命名导出 | 默认导出 |
| --- | --- | --- |
| 写法 | `export const a` | `export default ...` |
| 导入 | `import { a } ...` | `import anyName ...` |
| 一个模块可有几个 | 多个 | 最多一个 |
| 常见错误 | 忘记花括号、名称写错 | 错把默认导出当命名导出 |

**易错示例**：

```javascript
// user.js 只有 default 导出时：
// import { getUser } from './user.js'; // 通常报找不到命名导出
import getUser from './user.js'; // 正确
```

## 四、静态导入和动态导入 ⭐⭐⭐

静态导入写在模块顶层，构建工具容易分析依赖：

```javascript
import { formatDate } from './date.js';
```

动态导入 `import()` 返回 Promise，适合“用到时再加载”：

```javascript
async function openChart() {
  const { renderChart } = await import('./chart.js');
  renderChart();
}
```

例如后台系统的图表功能并非每个用户都会打开，把图表模块延后加载能减少首屏需要的代码量。

**注意：** 动态导入不等于一定产生独立网络文件。是否分包还取决于构建工具配置、模块图和部署方式。

## 五、普通 script、defer、async 与 module ⭐⭐⭐

| 方式 | 下载/执行特点 | 顺序注意点 |
| --- | --- | --- |
| 普通 `<script src>` | 解析器遇到时通常暂停解析等待执行 | 影响后续 HTML 解析 |
| `defer` | 下载可并行，HTML 解析完成后执行 | 多个 defer 按文档顺序 |
| `async` | 下载完成后尽快执行 | 不保证顺序，可能打断解析 |
| `type="module"` | 自动采用延迟执行行为（无 async 时） | 支持原生 import/export |

```html
<script src="./vendor.js" defer></script>
<script type="module" src="./main.js"></script>
```

**常见误区**：给 module script 额外加 `defer` 通常没有必要；并且跨源模块加载遵循 CORS 规则。

## 六、CommonJS 与 ESM 有什么区别？ ⭐⭐⭐

CommonJS 常见于历史 Node.js 生态：

```javascript
// math.cjs
module.exports = { add: (a, b) => a + b };

// app.cjs
const { add } = require('./math.cjs');
```

| 对比 | ES Modules | CommonJS |
| --- | --- | --- |
| 主要语法 | `import` / `export` | `require` / `module.exports` |
| 依赖分析 | 静态导入便于编译期分析 | require 调用可在运行时发生 |
| 常见场景 | 现代浏览器、现代前端工程 | 历史 Node.js 项目及部分工具链 |
| 导出特点 | 模块绑定可体现 live binding | 以模块导出对象和缓存为核心 |

Node.js 现在同时支持 ESM 和 CommonJS；具体采用哪一种由文件扩展名、package.json 等配置决定，不要一概说“Node.js 只支持 require”。

## 七、什么是依赖图和循环依赖？ ⭐⭐

比如 A 导入 B，B 导入 C，这些关系构成**模块依赖图**。

循环依赖：A 导入 B，B 又导入 A。它不必然报错，但可能遇到初始化时机问题、未初始化绑定（TDZ）等情况。

**建议**：

- 抽取公共逻辑到第三个模块。
- 避免两个业务模块互相承担职责。
- 不要把所有工具都集中到一个巨大 `utils.js`。

## 八、模块化、打包工具和代码分割的关系 ⭐⭐

- **模块化**：代码按文件和职责划分。
- **打包工具**：理解模块依赖，处理兼容性、资源引用与生产构建。
- **Tree Shaking**：尝试移除不使用的导出代码。
- **Code Splitting**：让代码按入口、页面或功能拆分，减少一次性下载量。

这是不同层次的概念；是否使用模块化，不取决于是否安装 Webpack 或 Vite。构建配置细节归档到 `10-Engineering`。

## 九、项目目录如何组织？

```text
src/
  api/          # 与服务端交互
  components/   # 可复用 UI 组件
  features/     # 按业务功能划分
  utils/        # 小型通用工具
  main.js       # 应用入口
```

**组织原则**：一个文件或模块负责相对清晰的事情；跨模块依赖尽量通过公开的导出接口，而不是任意修改全局变量。
