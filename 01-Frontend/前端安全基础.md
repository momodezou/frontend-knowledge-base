# 前端安全基础：哪些内容不能相信？

> **一句话理解**：前端安全最重要的习惯是：**用户输入、接口响应、URL 和第三方脚本都不能无条件信任**。前端负责安全呈现和减少攻击面，但最终权限与敏感操作必须由服务端把关。

> 本篇是前端日常安全编码入门；XSS、CSRF、CSP、Token 等原理可继续阅读 `07-Browser-Network/Web安全.md`。

## 一、最重要的原则：不要信任输入 ⭐⭐⭐

例如：用户输入昵称、搜索关键词，服务器返回商品说明，URL 中携带分享参数——它们都可能包含恶意内容或异常数据。

**不要把“来自后端”理解为“必然可信”**。后端数据可能来自用户、第三方服务或被污染的存储。

前端要做：

1. 按字段类型处理数据，做合理校验。
2. 把普通文本当成文本显示，不要随意当成 HTML。
3. 不拼接或执行不可信 JavaScript。
4. 对危险操作交给服务端再次鉴权、校验和记录。

## 二、XSS：把不可信文本当代码执行 ⭐⭐⭐

XSS（跨站脚本）可以简单理解为：攻击者把恶意脚本混入页面数据，浏览器错误地把它执行了。

### 危险写法

```javascript
const nickname = new URLSearchParams(location.search).get('name') ?? '';
document.querySelector('#nickname').innerHTML = nickname;
```

用户控制的字符串被当作 HTML 解析，可能出现脚本注入风险。

### 更安全的写法

```javascript
const nickname = new URLSearchParams(location.search).get('name') ?? '';
document.querySelector('#nickname').textContent = nickname;
```

`textContent` 把输入作为**文本**插入，不会把 `<`、`>` 解释成标签。

**但要注意**：`textContent` 适合文本节点，不代表在 HTML 属性、URL、脚本字符串等其他上下文里可以不做检查。不同输出场景需要对应的安全处理方式。

### 业务确实需要富文本怎么办？

比如文章编辑器需要显示 HTML，就不能简单地用 textContent，因为它会把标签文字也显示出来。

正确方向是：使用维护良好的 HTML 消毒库，对允许的标签和属性进行严格限制；必要时配合 CSP、Trusted Types 等机制。不要自己随手用一个正则表达式“过滤 `<script>`”来当作完整防护。

## 三、CSRF：浏览器可能自动携带身份凭据 ⭐⭐⭐

通俗理解：你登录了网站 A，浏览器保留了 A 的 Cookie；攻击者诱导你打开网站 B，B 想借你的浏览器向 A 发出非预期的请求。

CSRF 的关键不一定是拿到密码，而是**借用浏览器自动携带的会话凭据**。

常用防护：

- 服务端验证 CSRF Token。
- 为会话 Cookie 设置合理的 SameSite 属性。
- 对敏感写操作检查 Origin 等来源信息。
- 高风险操作增加二次认证。
- 不要用 GET 方法修改资金、权限等敏感状态。

**易错点**：CORS 并不等同于 CSRF 防护。CORS 主要限制跨源脚本读取响应；它不能自动阻止所有跨站请求产生副作用。

## 四、认证与授权：这两个词不要混淆 ⭐⭐⭐

- **认证（Authentication）**：你是谁？例如用户登录。
- **授权（Authorization）**：你能做什么？例如普通员工能否删除管理员账号。

```javascript
// 前端可以根据权限决定按钮是否显示
if (user.permissions.includes('order:delete')) {
  deleteButton.hidden = false;
}
```

这只是**用户界面体验控制**。用户可以修改浏览器代码或绕过按钮直接请求 API，因此服务端仍然必须校验真实权限。

**面试高频**：“隐藏删除按钮是否就完成了权限控制？”——没有，真正的授权必须在后端实施。

## 五、Cookie、Token、localStorage 的风险 ⭐⭐⭐

| 位置/手段 | 主要特性 | 需要注意 |
| --- | --- | --- |
| HttpOnly Cookie | JS 无法直接通过 document.cookie 读取 | 仍要考虑 CSRF，且无法根除 XSS |
| localStorage | 同源 JS 可以读写 | 一旦同源 XSS 成功，敏感 Token 可能被读取 |
| sessionStorage | 按源和标签页会话隔离 | 同源脚本依然可访问 |
| Authorization Header | 可以由应用代码显式附加凭据 | 避免泄露到日志、URL、错误上报 |

不要宣称“Token 放在哪里绝对安全”。实际选型取决于认证模型、浏览器环境、XSS/CSRF 防护和服务端设计。

## 六、HTTPS 和混合内容 ⭐⭐

HTTPS 通过 TLS 保护传输链路，帮助抵抗窃听、篡改和伪造服务器。

但 HTTPS 页面中仍然请求 `http://` 脚本或接口时，可能遇到**混合内容（Mixed Content）**问题，浏览器通常会阻止危险的不安全子资源。

```html
<!-- HTTPS 网站不要加载 HTTP 脚本 -->
<script src="http://example.com/app.js"></script>
```

正确做法是改用 HTTPS 资源并确认目标域名和证书可信。

## 七、前端打包产物不能藏秘密 ⭐⭐⭐

很多前端项目会使用 `.env` 或构建工具的环境变量。

**误区**：只要写到前端 `.env` 里，别人就看不到。

只要某个值被构建进浏览器可下载的 JS、HTML 或 CSS，用户就有机会拿到它。所以：

- **不能**把数据库密码、私有 API Key、云服务密钥放入前端打包产物。
- 前端允许公开的配置，如公开 API Base URL、公共资源地址等，可以按工具约定暴露。
- 真正需要保密的密钥必须放在服务端，并由服务端安全访问第三方服务。

## 八、外部链接与消息通信的安全细节 ⭐⭐

### 外部链接

```html
<a href="https://example.com" target="_blank" rel="noopener noreferrer">
  打开外部网站
</a>
```

现代浏览器对 `target="_blank"` 通常已有隐含的 noopener 行为，但显式写上有利于表达意图。需要根据业务考虑是否发送 Referer。

### iframe / postMessage

```javascript
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://trusted.example.com') return;
  // 再验证 event.data 的结构，才做业务操作
});
```

跨窗口消息不能只看“收到了消息”，还要验证发送方来源及消息结构。

## 九、第三方依赖与供应链安全 ⭐⭐

- 优先安装维护良好、来源明确的包。
- 避免随意执行网络上复制来的安装脚本。
- 关注依赖风险告警和版本更新。
- 代码审查时留意第三方脚本对页面和用户数据的访问能力。
- 不把 `.env`、私钥、生产 Token 推送到公开 Git 仓库。

一旦敏感信息已经提交，即使删除当前文件，也可能仍保留在 Git 历史中；需要立即撤销/轮换密钥，并根据情况处理历史记录。

## 十、前端安全检查表

- [ ] 用户或接口字符串显示在页面时优先使用安全 DOM API。
- [ ] 需要富文本时有明确的消毒规则。
- [ ] 服务端对每个敏感接口执行权限校验。
- [ ] 登录凭据存储有经过评估的 XSS、CSRF 防护方案。
- [ ] API 凭据不会被打包进前端资源。
- [ ] 不把敏感数据放在 URL 查询字符串。
- [ ] 第三方脚本、iframe 消息和外部链接经过信任评估。
- [ ] 公开仓库中没有密钥、客户数据或公司未授权源码。
