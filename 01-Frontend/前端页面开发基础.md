# 前端页面开发基础：把一个页面真正做完整

> **一句话理解**：开发页面不只是把设计稿画出来，而是让页面在**正常、加载、失败、无数据、不同设备**等状态下都能稳定使用。

## 一、前端开发在做什么？ ⭐⭐⭐

一个前端页面通常要完成三个任务：

1. **展示内容**：HTML 定义结构，CSS 控制外观。
2. **处理交互**：JavaScript 响应点击、输入、滚动等操作。
3. **和服务端协作**：请求数据，处理登录、保存、搜索等业务行为。

以商品列表页为例：

```text
用户打开页面
  → 加载界面
  → 请求商品数据
  → 显示列表或空状态
  → 用户搜索/筛选
  → 发起新请求
  → 更新结果
  → 错误时提供重试
```

**高频误区**：只考虑“请求成功且有数据”的情况，页面上线后容易出现白屏、按钮卡死或重复提交问题。

## 二、页面应该有哪些基本状态？ ⭐⭐⭐

| 状态 | 用户看见什么 | 开发者要考虑什么 |
| --- | --- | --- |
| 初始 | 页面基础结构 | 是否有合理的默认布局 |
| Loading | 加载中提示/骨架屏 | 不要让用户误认为卡住 |
| Success | 数据内容 | 处理正常交互 |
| Empty | 暂无结果 | 说明原因、可否清除筛选 |
| Error | 加载失败 | 友好说明、提供重试入口 |
| Submitting | 正在提交 | 避免无意识重复提交 |

设计一个页面时，至少要问：“没网怎么办？接口返回空数组怎么办？用户连续点击怎么办？”

## 三、一个小型列表页的原生实现 ⭐⭐⭐

这个示例演示**请求、加载状态、错误处理和安全显示文本**。API 地址需替换成你自己的后端接口。

```html
<section aria-labelledby="products-title">
  <h1 id="products-title">商品列表</h1>
  <p id="status" role="status" aria-live="polite"></p>
  <ul id="products"></ul>
  <button id="reload" type="button">重新加载</button>
</section>
```

```javascript
const list = document.querySelector('#products');
const status = document.querySelector('#status');
const reload = document.querySelector('#reload');
let controller;

async function loadProducts() {
  controller?.abort(); // 取消上一轮仍在进行的请求
  controller = new AbortController();
  const signal = controller.signal;

  status.textContent = '正在加载…';
  reload.disabled = true;
  list.replaceChildren();

  try {
    const response = await fetch('/api/products', { signal });
    if (!response.ok) throw new Error(`HTTP ${response.status}`);

    const products = await response.json();
    if (!Array.isArray(products)) throw new Error('数据格式不正确');

    if (products.length === 0) {
      status.textContent = '暂时没有商品';
      return;
    }

    const fragment = document.createDocumentFragment();
    for (const product of products) {
      const li = document.createElement('li');
      li.textContent = String(product.name ?? '未命名商品');
      fragment.append(li);
    }
    list.append(fragment);
    status.textContent = `共 ${products.length} 件商品`;
  } catch (error) {
    if (error.name === 'AbortError') return;
    status.textContent = '加载失败，请检查网络后重试';
    console.error(error);
  } finally {
    if (!signal.aborted) reload.disabled = false;
  }
}

reload.addEventListener('click', loadProducts);
loadProducts(); // 需确保 DOM 已创建，例如脚本使用 defer
```

**为什么这样写？**

- `response.ok`：`fetch()` 遇到 HTTP 404、500 不会自动抛出异常，需要主动检查。
- `AbortController`：避免旧请求结果覆盖新请求，或用户离开页面后继续处理不需要的结果。
- `textContent`：把接口字符串当作文本显示，避免直接解析不可信 HTML。
- Loading/Empty/Error：保证失败时用户也知道下一步可以做什么。
- `disabled`：避免用户连续触发相同操作；更复杂的并发场景还需业务幂等保障。

## 四、前后端分工与 API 契约 ⭐⭐⭐

- 前端：输入、交互、呈现和部分体验校验。
- 后端：数据存储、权限校验、业务规则和最终安全校验。
- 接口契约：双方约定请求方法、字段、状态码、错误结构等。

例如一个列表 API 可以约定：

```json
{
  "items": [{ "id": 1, "name": "示例商品" }],
  "total": 1,
  "page": 1,
  "pageSize": 20
}
```

前端不能假设接口永远返回正常对象。应处理网络错误、超时/取消、字段缺失及服务端错误。

## 五、CSR、SSR、SSG：内容从哪里来？ ⭐⭐⭐

| 方式 | 通俗解释 | 常见场景 |
| --- | --- | --- |
| CSR（客户端渲染） | 浏览器加载 JS，再在客户端生成主要内容 | 交互复杂的后台系统 |
| SSR（服务端渲染） | 服务器先生成 HTML，浏览器再完成交互初始化 | SEO、首屏体验要求高的站点 |
| SSG（静态站点生成） | 构建时预先生成 HTML | 文档、博客、内容变化不频繁的页面 |

**易错点**：SSR 不等于“完全不需要 JS”，很多 SSR 应用还要进行 **Hydration（水合）**，给服务器输出的 HTML 接上客户端交互。SSR 也不意味着一定更快，需要考虑服务器响应与 JS 成本。

## 六、可访问性、适配和加载性能要从开始考虑 ⭐⭐

- 使用正确的按钮、链接、表单标签，而不是单纯靠 div 点击。
- 为图片提供有意义的 `alt`，为表单提供 `label`。
- 页面在窄屏、长文本、大字号下不应横向溢出。
- 首屏关键资源优先加载，非关键资源按需加载。
- 不要随意把几千条列表一次性渲染成大量 DOM 节点。

布局细节在 `06-CSS`，资源加载和性能指标在 `07-Browser-Network`，这里重点是完整的页面开发过程。
