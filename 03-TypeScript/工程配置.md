# TypeScript 工程配置：tsconfig、声明文件与 Vue3 / React 实践

> **定位**：面向真实前端项目，解释为什么要配置 TypeScript，以及如何处理常见报错。
>
> **重要**：编译配置会随 TypeScript、Vite、Vue、React 和 Node 版本变化。本篇提供通用思路，具体项目以其工具链官方模板与版本文档为准。

## 一、`tsconfig.json` 决定什么？ ⭐⭐⭐

`tsconfig.json` 主要定义 TypeScript 项目的源码范围、类型检查严格程度、JavaScript 输出行为、模块与解析规则等。它**不会替代** Vite、Webpack 或 Node 的全部运行时配置。

### 示例：适合现代浏览器打包工具项目的基础配置

> 以下是演示用的核心配置，不是覆盖所有 Vue / React 项目需求的“万能模板”。

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noEmit": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noFallthroughCasesInSwitch": true
  },
  "include": ["src/**/*.ts", "src/**/*.tsx", "src/**/*.d.ts"]
}
```

**注意**：如果项目含 Vue 单文件组件、Vite 特定类型定义、不同运行环境的 `tsconfig`，还需补充对应的 `include`、`types`、`jsx` 或项目引用配置。

### 高频选项解释

| 选项 | 主要作用 | 容易误解的地方 |
|---|---|---|
| `strict` | 启用一组更严格的检查 | 并不意味着所有潜在运行时错误都能被检测到 |
| `target` | 指定 JS 语法输出目标 / 默认库影响 | 与 `lib`、打包器兼容性目标不是一回事 |
| `lib` | 提供标准 API 与环境类型声明 | 不会自动为旧浏览器注入 polyfill |
| `module` | 控制模块语义/输出形式 | 与 `moduleResolution` 需要匹配运行环境 |
| `moduleResolution` | 决定如何查找模块及类型 | Vite 通常考虑 `Bundler`，Node 原生 ESM 通常考虑 `NodeNext` |
| `noEmit` | 不让 `tsc` 生成 JS 等输出文件 | 适合构建由 Vite / SWC / Babel 等完成的项目 |
| `skipLibCheck` | 跳过声明文件的完整类型检查 | 不等于忽略自己代码中的类型错误 |
| `noUncheckedIndexedAccess` | 索引读取更保守，可能加 `undefined` | 数组索引和字典查找需要额外处理 |
| `exactOptionalPropertyTypes` | 更严格区分“缺失”和“显式 undefined” | 迁移旧项目可能出现兼容调整 |

## 二、`strict` 为什么非常重要？ ⭐⭐⭐

```ts
function getLength(input: string | null): number {
  // strictNullChecks 打开时，必须处理 null
  return input === null ? 0 : input.length;
}

const items = ['A', 'B'];
const first = items[0];
// 开启 noUncheckedIndexedAccess 时，first 类型为 string | undefined
if (first !== undefined) console.log(first.toUpperCase());
```

**高频面试问题**：`strict` 与 `noUncheckedIndexedAccess` 解决的问题是否相同？——不相同，后者是独立的增强检查选项，不是 `strict` 自动打开的全部内容。

## 三、模块系统与路径别名 ⭐⭐⭐

### ES Modules 与类型导入

```ts
import type { User } from './models';
// 仅为类型依赖，不需要在运行时引入 User
```

`import type` 有助于清晰区分类型与运行时依赖，配合 `verbatimModuleSyntax` 等选项可避免意外的导入输出行为。

### 路径别名要两边配置

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

这段是说明 `compilerOptions` 的**配置片段**，不是完整 `tsconfig.json`。TypeScript 的 `paths` 主要影响模块解析，**不会自动改写生成代码中的导入路径**。如果使用 Vite 等构建器，也要保证打包器端别名一致；或者使用与工具链兼容的别名方案。

## 四、`.d.ts` 类型声明文件与第三方库 ⭐⭐⭐

类型声明文件用于描述 JavaScript 代码、库或模块提供的类型结构，通常不会生成可执行实现。

### 为没有类型定义的模块声明一个基本接口

```ts
// src/types/untyped-lib.d.ts
declare module 'untyped-lib' {
  export function formatDate(value: Date): string;
}
```

使用时可以 `import { formatDate } from 'untyped-lib'`，但前提是项目确实安装或提供了该模块的运行时实现。声明文件**不会凭空创建实现**。

### 描述环境变量（Vite）

```ts
// src/vite-env.d.ts
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_BASE_URL: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}
```

> 这里是使用 Vite 的示例，需安装 Vite 才能解析相关类型；`VITE_` 前缀的变量可能暴露到客户端，**绝不能存放服务器密钥**。

### 不要滥用 `declare module 'xxx';`

空的声明可能使模块退化为 `any`，只是暂时掩盖类型问题。优先查找库自带类型、维护中的类型包或手动补充真实接口。

## 五、Vue3 + TypeScript 实践 ⭐⭐⭐

Vue 项目常见实践：

- 在 `<script setup lang="ts">` 中使用 TS。
- 使用 `defineProps` / `defineEmits` 指定组件接口。
- 用 `ref<T>()` 说明初始值无法充分推导的状态。
- 使用 `vue-tsc` 检查 `.vue` 单文件组件中的类型。
- 参考项目脚手架创建的 `tsconfig`、`env.d.ts` 和 Vite 配置。

```vue
<script setup lang="ts">
import { ref, computed } from 'vue'

interface Props {
  title: string
  count?: number
}
const props = withDefaults(defineProps<Props>(), { count: 0 })
const emit = defineEmits<{ change: [next: number] }>()

const current = ref<number>(props.count)
const displayText = computed(() => `${props.title}: ${current.value}`)

function increase() {
  current.value += 1
  emit('change', current.value)
}
</script>

<template>
  <button @click="increase">{{ displayText }}</button>
</template>
```

**易错**：`ref<User>()` 在未赋初始值时，`.value` 仍可能为 `undefined`，使用前应处理空值；`reactive` 也不建议通过过度复杂的显式泛型来强制声明返回类型。

## 六、React + TypeScript 实践 ⭐⭐⭐

在支持 React JSX 的工程中（例如使用 `jsx: react-jsx`），组件 props、事件、状态类型可以保持清晰。

```tsx
import { useState } from 'react';

type User = { id: number; name: string };

type UserCardProps = {
  user: User;
  onSelect: (id: number) => void;
};

export function UserCard({ user, onSelect }: UserCardProps) {
  const [expanded, setExpanded] = useState<boolean>(false);
  return (
    <div>
      <button onClick={() => onSelect(user.id)}>{user.name}</button>
      <button onClick={() => setExpanded(v => !v)}>
        {expanded ? '收起' : '展开'}
      </button>
    </div>
  );
}
```

**易错**：`useState([])` 在没有上下文时可能推导出过窄类型（例如 `never[]`），应根据真实数据写 `useState<User[]>([])`。React 代码示例需要安装 `react` 及对应的类型声明，不能在纯 TS 环境中独立检查 JSX。

## 七、TypeScript 与 Vite 的构建、检查分工 ⭐⭐⭐

**常见误区：** “`vite build` 成功就说明 TypeScript 没有类型错误”。Vite 默认重点做转换和打包，**不等价于独立完整类型检查**。

项目可以在 package.json 中为类型检查配置单独命令（示例）：

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "npm run typecheck && vite build"
  }
}
```

对于 Vue 单文件组件，可用适配项目的 `vue-tsc` 命令代替 `tsc` 的基础检查。使用项目引用（project references）时，还应遵循脚手架生成的构建检查流程。

## 八、实际问题排查：按原因归类 ⭐⭐⭐

| 常见问题 | 优先检查 |
|---|---|
| Cannot find module | 包是否已安装、路径是否正确、`moduleResolution`、库类型声明 |
| 隐式 any | 参数/返回类型、是否缺少泛型约束、`strict` 设置 |
| 对象可能为 null / undefined | 空值建模和判空逻辑，避免直接 `!` |
| `*.vue` 找不到类型 | `vue-tsc`、Vue 依赖、SFC 配置、`include` |
| `import.meta.env` 报类型错误 | Vite 类型引用、环境声明、文件是否纳入项目 |
| 类型别名可用但运行时无法导入 | 类型擦除、`import type`、是否有真实 JS 导出 |
| 本地正常但 CI 报错 | Node / TS / 包管理器版本、锁文件、大小写敏感路径 |

排查建议按顺序：**复现最小代码 → 查看完整诊断 → 核对 tsconfig → 检查依赖和类型定义 → 修复真实模型**。不要把关闭严格检查或到处写 `as any` 作为常规解决方案。
